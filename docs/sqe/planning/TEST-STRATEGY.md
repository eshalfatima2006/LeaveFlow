## API, data generation and persistence

Use Phase 1 input inventory rather than invented fields: required dates; optional vacation/permit/personal type with vacation default; optional blank nonnull trimmed note≤280; read-only owner/status; manual approved/rejected decision value and route k. No max leave duration, future-only dates or per-year filtering exists. Include absent/null/blank/type/enum classes, supported and wrong methods/media, real invalid tokens, ownership injection and output schemas. Test exact guards' precedence (401; role403; status400; scoped404; self403; state409), numerical/date boundaries, inclusive overlap, absent balance, zero days, final-state repeats, event-disabled/enabled/failure paths and relevant supporting GETs. Set one invalid field per partition case; separately identify intentional multi-condition combinations.

The team will author/repair a versioned OpenAPI spec because current function-view inference omits useful schemas. Generator reads paths/methods, required/nullability/default/type/format/enum/maxLength, creates all identified valid/invalid classes and below/at/above every applicable ordered bound, tags infeasible or nonordered BVA as N/A with reason, and emits reproducible cases consumed directly by API tests. A case manifest records spec hash, constraint path, EP/BVA class, seed, expected oracle and actual test ID. Omission differs from null; trimming/coercion and ignored unknown/read-only fields must match actual behavior.

Cross-field date order, overlap, available allowance, role/team/self and state require a reviewed rule manifest/fixtures and cannot be invented as scalar maxDays=26. Change **two constraints** in a controlled spec variant (proposed note maxLength and leave_type enum), regenerate, show diff and API consumption. Label expected contract-drift failures against unchanged baseline; after separately authorized coordinated code/spec change rerun. Do not claim changing spec alone changes the application.

Read back original k, owner, dates/type/note, state, decided_by/at, count and employee-derived balance after success **and rejection**. Audit fields are not serialized, so ORM assertions are necessary. No balance row decrement occurs; approved-days sum changes. Repeated W2 is409; repeated W1 overlapping pending/approved ordinarily400, not idempotent201. Concurrency needs synchronized independent DB connections, bounded waits and real PostgreSQL row-lock semantics; SQLite runs cannot prove those guarantees.

## Mutation, Sonar and CI sequence

First make isolated tests, coverage, generator, browser execution and mutation reproducible locally. Then students add required PR jobs; verify each result is associated with the candidate SHA and prevent merge/deployment when a required job fails, is missing, is skipped or returns a below-threshold gate. No success overrides (`continue-on-error`, `|| true`) may mask a required check. A staged rollout of tools is an implementation sequence, not a final reduced gate. Existing `.github/workflows/ci.yml` currently runs upstream backend tests/builds/service checks; it lacks the assignment's team tests/Sonar/mutation gates. Existing `auto-release.yml:4–19` listens to successful main CI, so team must connect release eligibility to the full gate and inspect its tolerated tag-discovery command (:50); do not treat it as an assignment quality-gate implementation.

Proposed gates (not instructor values): mutation adjusted score≥85%, no timeouts/unclassified mutants; Sonar zero new confirmed bugs/vulnerabilities, all security hotspots reviewed, new-code duplication≤3%, plus assignment coverage100/100. Record all requested Sonar metrics (complexity, duplication, smells, bugs, vulnerabilities, coverage, debt and ratings) and their interpretation, including metrics not gated numerically. Confirm free/open-source Sonar deployment, PR scan/gate capabilities and runner capacity; do not assume a paid feature or SaaS access exists.

Mutation adjusted score=K/(K+L)×100 where K killed and L live non-equivalent, after independently justified equivalents E; also report raw K/(K+L+E)×100 and invalid/timeout counts. Empty denominator=N/A, never100%. At least two custom rule operators proposed: allowance `>`→`>=`; overlap inclusive bounds/status-set mutation. Analyze ≥15 genuine surviving mutants (equivalent/missing test/weak assertion), kill killable ones, keep before/after evidence. If fewer than15 exist, report all, extend meaningful approved mutation scope and ask instructor how to meet the requirement; never create fake survivors or waive it silently. A1 proposes final gate after a pilot; 85% is provisional and must not replace mandated full coverage.

## Performance and recovery protocol

Proposed PERF-001 operation: valid **POST /api/requests/** with fixed-duration, nonoverlapping windows assigned deterministically to each VU/iteration. Preallocate synthetic users with no prior approved leave (pending does not reserve allowance), known balances and enough disjoint windows; bound requests per run and record actual fixture manifest. Keep starting rows and dates identical per replicate; do not reuse a mutated database. Set REDIS_URL empty for the declared core-workflow profile; notification-enabled measurements, if added, are separate, clearly labelled experiments.

Provisional team thresholds for **each** load level: p95≤500ms and unexpected HTTP/transport failures<1%. These are proposed interactive-local-demo budgets, not measured results or professor-supplied targets. Validate/approve before executing; do not move them after seeing results without a documented new experiment. Test 1VU and5VUs twice each, ramp to target, measure **≥60 seconds after target reached**, exclude warm-up/setup, capture all-operation latency (including failures), expected201/check success, rps, errors and row counts; do not hide errors by latency filtering. Same tested SHA, machine, software, dataset, pacing and settings; reset only dedicated experiment DB. Report sample sizes and percentiles/error rates separately per run, no average masking a failing run. SQLite contention and growth of overlap/approved-day queries affect results; record DB engine and do not generalize to production PostgreSQL or full notifications. Choose PostgreSQL explicitly for a separate comparable profile if necessary.

REC-001 injects a controlled DB/ORM failure **before a W1 insert completes**, using a local test double at the create seam; ensure nothing persisted, restore dependency, retry same payload, assert exactly one pending k, caller ownership, null audit, unchanged balance, correct response and no failed-attempt event. Add W2 atomic rollback/restore/retry assertions at its save/event boundary and after-commit Redis outage distinction: swallowed publish failure does not undo an already committed decision. Lost response retries must read state to avoid duplicates; do not pretend Redis loss before callback prevents a write. Fault injection is later test work, with no live infrastructure outage in Phase 2.

## Coverage terminology (v0.2)

Lecture 20 defines the API coverage criteria: the ten REST criteria and test coverage levels TCL0–TCL7 (path, operation, parameter, parameter value, request and response content type, operation flow, status-code class, status code, response body properties), measured against the reviewed OpenAPI document and reported **together with** technique coverage (EP, three-point BVA, decision tables, state transitions).

Lecture 15 defines state-transition levels: all states < valid transitions (0-switch) < all transitions (valid plus every invalid cell). The API state table already reaches all transitions through A2.1.

Coverage **criteria** are targets. **Achieved** coverage is only what executed evidence shows.
